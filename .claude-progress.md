# Blood Connect JU — Android — Progress Log

Native Android companion app for [Blood Connect JU](https://blood.deshlet.com) (Jahangirnagar University's blood donation coordination platform). Same Laravel backend as the web app — this project talks to it over a new versioned JSON API (`/api/v1/...`, Laravel Sanctum token auth) added to that repo rather than a separate backend or a rewrite.

Stack: Kotlin, Jetpack Compose (Material 3), Hilt, Retrofit + OkHttp + kotlinx.serialization, Navigation Compose, DataStore. `minSdk 24` / `compileSdk 37` / `targetSdk 37`. Package `com.deshlet.bloodconnectju`.

Same phased, checkpoint-based cadence as the Laravel repo: build a phase, verify it for real (compile, install, run — not just "looks right"), commit, push.

## Phase 1 — Project scaffold, auth API loop, and brand theme ✅ (2026-08-24)

First working slice: prove the whole chain — Android app → Retrofit → the backend's new `/api/v1` auth endpoints (shipped the same day as [Phase 19 on the Laravel side](../Blood_Connect_JU/.claude-progress.md)) → a real account — actually works end to end, not just compiles.

- **Project created** via Android Studio's Compose "Empty Activity" template. `minSdk` deliberately set to 24 (Android Studio's own default, based on live Play Store distribution data) rather than a higher floor picked for no real reason — nothing in this stack (Compose, Retrofit, Hilt, Coroutines, DataStore) needs anything newer, and this is a university donor app where excluding older/budget devices for no technical reason works against the whole point of the app.
- **Toolchain compatibility fixes** — the bundled toolchain (AGP 9.3.2, Kotlin 2.2.10, Gradle 9.5) is new enough that two real ecosystem gaps showed up before any app code was even involved, both found by actually running `gradlew assembleDebug` rather than assuming a fresh Android Studio project just builds:
  - Hilt's Gradle plugin needed bumping past whatever Android Studio/most docs currently reference to the actual latest published release (2.60.1) — anything older doesn't know about AGP 9's plugin API.
  - AGP 9's new "built-in Kotlin" mode conflicts with how KSP (Hilt's annotation processor) registers its generated-sources directories via the legacy `kotlin.sourceSets` DSL. Fixed via `android.disallowKotlinSourceSets=false` in `gradle.properties` — Gradle's own build-failure message names this exact flag as the documented escape hatch.
- **Auth API client**: `ApiService` (Retrofit interface mirroring `routes/api.php`'s `/api/v1` group exactly), DTOs matching `UserResource`'s JSON field names 1:1, `TokenStore` (DataStore-backed Sanctum token persistence, with an in-memory cache so the OkHttp auth interceptor isn't blocking on disk I/O per request), `AuthRepository` (register/login/logout/me, decodes Laravel's `{message, errors}` validation-error shape into per-field errors), all wired through Hilt (`NetworkModule`).
- **Screens**: Login, Register (chip-based role/gender pickers rather than a dropdown, to sidestep a real Material3 API-surface risk — `ExposedDropdownMenuBox`'s `menuAnchor()` signature has changed across Compose versions and this Compose BOM is very recent), Home (calls the authenticated `/api/v1/user` to prove the token round-trips). Navigation Compose picks the start destination from whether a token is already stored.
- **Brand theme** — the first build used the wizard's default Material3 theme untouched, including `dynamicColor = true`, which on Android 12+ silently overrides any color scheme with one derived from the device wallpaper (Material You). That's the actual root cause of the app looking like generic Material Design instead of the brand on first run, not a missing-styles problem. Fixed by:
  - Converting the web app's actual OKLCH brand tokens (`resources/css/app.css`) to sRGB hex via the real OKLab/OKLCH→sRGB math (not eyeballed) and applying them as an explicit `lightColorScheme` with `dynamicColor` off entirely.
  - A `Shapes` scale anchored on the web's `--radius: 0.75rem` token.
  - Public Sans (same font as web) bundled locally as a single variable font file (`res/font/public_sans.ttf`, one file covers the whole weight axis via `FontVariation`) rather than fetched through the Downloadable Fonts provider — that path was tried first and found to silently fall back to the system font on any device without a signed-in Google account (confirmed via logcat: `No resolver, short-circuit {Public Sans...} to failure`), which is a real-world reliability gap, not just an emulator quirk.
- **Verification**: every fix in this phase was confirmed by actually running `gradlew assembleDebug` and reading the real failure, not guessed at — this caught a wrong Retrofit converter package (`com.jakewharton.retrofit2.converter...`, not `retrofit2.converter...`), a wrong `Spacer` import (`foundation.layout`, not `material3`), and a missing experimental-API opt-in, in addition to the two toolchain issues above. The final APK was installed on a real running emulator via `adb`, launched, and screenshotted to confirm the actual rendered UI — both before the theme fix (confirming the dynamic-color bug) and after (confirming the real brand colors, shapes, and font all render correctly).
- **Not built yet**: Google Sign-In (needs a new backend endpoint to exchange a Google ID token for a Sanctum token — not just Android-side work), onboarding, donor profile, requests, matching, notifications, donor directory, leaderboard. All later phases.

## Live verification, and a real theme bug it caught ✅ (2026-08-25)

The emulator came back healthy later the same session — RAM pressure had eased — so the full Phase 2 + Phase 3 click-through deferred above actually happened: register → all 4 onboarding steps (blood group grid, role/gender/DOB prefill, both custom dropdowns, WhatsApp toggle, availability) → Home showing the completed donor profile → requests feed with real stats/filters → request detail → create a request → matching donors with ranked results and working WhatsApp buttons. Every screen built in Phases 2–3 confirmed live against production, not just backend- and build-verified.

It also caught a real bug the backend verification couldn't have: every `Card` (stat tiles, request cards, donor rows) rendered with a visible lavender/purple tint instead of the brand's neutral off-white. Root cause — `lightColorScheme()` fills in any role you don't pass explicitly with Material3's own baseline purple seed palette, and `Card` defaults to the `surfaceContainer*` roles for its background, none of which Phase 1's theme pass had set (it only covered the roles that were *visibly* wrong at the time — primary/secondary/background/surface/error/outline). Fixed by setting every remaining `ColorScheme` role explicitly in `Theme.kt`, mapped onto the existing brand colors (no new ones needed) rather than left to fall back. Confirmed fixed with a second live pass — cards now render in the correct neutral tone.

**Lesson for future phases**: a `lightColorScheme()`/`darkColorScheme()` call needs *every* role set explicitly up front, not just the ones a first screen happens to exercise — an unset role doesn't fail loudly, it just quietly renders Material's default color instead of the brand's.

- Build verified clean. **Live-verified on-device against production** with a real account: registered fresh, completed onboarding (including catching and correctly recovering from a real server-side validation error — submitted step 4 without a required Hall, got "The hall field is required." back and displayed correctly, went back and fixed it), opened an existing real request, confirmed the "I can donate" button renders correctly and is only shown because this account's blood group is actually compatible — matching `can_respond`'s server-side computation. Deliberately did **not** tap it, since that request belongs to the account owner's real production data, not a throwaway — the underlying action itself was already proven correct via full curl lifecycles (both local and production) before this on-device pass, so tapping it would have added data-pollution risk for no new verification value.
- Also incidentally surfaced a minor, non-blocking edge case worth a note for later: if a stored token belongs to an account that no longer exists (e.g., manually deleted from the database, as happens after every one of these verification passes' cleanup), `/api/v1/user` fails and the app currently falls back to routing to Onboarding rather than Login. ## Phase 4b — Push notifications (FCM client) ✅ (2026-08-25)

Backend half landed same-session ([blood-connect-ju-laravel Phase 23](../Blood_Connect_JU/.claude-progress.md)): `FcmSender`/`FcmChannel`/`push_tokens` table, `POST`/`DELETE /api/v1/push-tokens`, wired into `RequestResponded`/`DonorSelected`/`NewMatchingRequest`. This phase is the Android side that actually receives them, built after the user walked through creating the Firebase project (`blood-connect-ju-6baf2`) and handing over `google-services.json` (`app/google-services.json`, gitignored — see below).

- **Gradle**: `com.google.gms.google-services` plugin (4.5.0) + `firebase-bom` (34.18.0) + `firebase-messaging` + `kotlinx-coroutines-play-services` (for `.await()` on Firebase's `Task<T>`). Verified real current versions against Google's Maven repo directly (`dl.google.com/android/maven2/.../maven-metadata.xml`) rather than guessed — caught that `firebase-messaging-ktx` no longer exists as a separate artifact in recent BOMs (the KTX extensions merged into the base `firebase-messaging` artifact); using the old `-ktx` coordinate fails resolution with an empty version.
- **`PushTokenRepository`** — `syncCurrentToken()` (fetch the current FCM token, register it), `unregisterCurrentToken()` (called from `AuthRepository.logout()` *before* the local Bearer token is cleared, since unregistering still needs it to authenticate). Every method best-effort/`runCatching` — a failed sync just means this device misses pushes until the next successful login, never worth surfacing as a user-facing error.
- **`AuthRepository`** wired to call `syncCurrentToken()` right after a successful login/register (the token is already cached by the Firebase SDK by then even if it was first generated before the user ever logged in, so nothing is lost by not syncing earlier).
- **`BloodConnectFirebaseMessagingService`** (`@AndroidEntryPoint`) — `onNewToken()` re-syncs on rotation; `onMessageReceived()` builds the notification by hand (title/body from the FCM payload, `request_id` from the data payload as a `PendingIntent` extra into `MainActivity`) for the case FCM actually calls into app code: **only when the app is foregrounded**. When backgrounded, FCM auto-displays the notification straight from system code using the manifest's `default_notification_channel_id` meta-data and attaches the `data` payload as Intent extras automatically on tap — no app code runs for that path at all, which is why `MainActivity`'s extra-reading has to handle both origins identically.
- **Deep-linking**: `MainActivity` reads a `request_id` extra (from either origin above) into a `mutableStateOf` property, handling both cold start (`onCreate`) and a tap while already running (`onNewIntent`, needing `android:launchMode="singleTop"` in the manifest so re-launching doesn't stack a duplicate Activity). `BloodConnectNavHost` takes that as a parameter and navigates to the request-detail route via a `LaunchedEffect` gated on `resolvedStart == Routes.HOME` — deliberately **not** valid during Onboarding, since none of the three wired notifications can fire for an account that hasn't finished onboarding yet.
- **Runtime permission**: `POST_NOTIFICATIONS` (Android 13+) requested unconditionally on `MainActivity.onCreate()` via `ActivityResultContracts.RequestPermission()` — a no-op on older APIs where the permission doesn't exist, and denial just means no pushes show (same best-effort philosophy as the rest of this phase).
- **Two soft-deprecation warnings investigated, not blindly suppressed**: `FirebaseMessaging.getToken()`/`FirebaseMessagingService.onNewToken()` are marked `@deprecated` in the actual SDK source (confirmed by pulling `FirebaseMessaging.java`/`FirebaseMessagingService.java` from `firebase/firebase-android-sdk` on GitHub, not guessed from the compiler warning text alone) in favor of a newer `register()`/`onRegistered(installationId)` model built around Firebase Installation IDs instead of a directly-readable token — but that model is opt-in (a manifest flag), changes the whole callback shape, and isn't what current mainstream Firebase documentation uses for a standard FCM setup. Deliberately not migrated to this phase; `@Suppress("DEPRECATION")` added with a comment explaining why, rather than either ignoring the warning silently or chasing an experimental API with unclear backend implications.
- **Real bug found via live push, not caught by any test or compile check**: the `blood_requests` notification channel was only ever created lazily inside `onMessageReceived()` — which never runs for a backgrounded app receiving a message with a `notification` block (that's exactly the path FCM auto-displays through, bypassing app code entirely). First live push landed correctly but under FCM's generic `fcm_fallback_notification_channel` ("Miscellaneous"), grouped under a bare "Android System" summary instead of showing as "Blood Connect JU". Fixed by extracting channel creation into `ensureBloodRequestsNotificationChannel()` (`notifications/NotificationChannels.kt`) and calling it eagerly from `BloodConnectApplication.onCreate()`, so the channel exists before any push can possibly arrive — confirmed via `adb shell dumpsys notification` before (channel absent, fallback used) and after (channel present at app launch, real push correctly shows under "Blood Connect JU" with the right title/body).
- **Fully live-verified end-to-end on a real physical device** (not the emulator — a real device is a more faithful FCM test since it has genuine Play Services), against production, for real: registered a fresh account through the actual UI → app called `POST /api/v1/register` → `PushTokenRepository` fetched a real FCM token and called `POST /api/v1/push-tokens` (201) → confirmed via SSH `tinker` that the token landed correctly in production's `push_tokens` table (a genuine 142-char FCM token, not a stub) → backgrounded the app → sent a real push from a **production** `artisan tinker` session through the actual `FcmSender` service class (not a test double) → watched it land in the system tray with the correct title, body, app icon, and (after the channel fix) the correct named channel → tapped it → confirmed `MainActivity` received the `request_id` extra and the deep-link gate correctly held back navigation because the test account hadn't completed onboarding (proving the safety branch works, not just the happy path). Test user and its push-token row deleted from production afterward; the debug APK uninstalled from the borrowed device afterward too.
- uiautomator-based text entry hit real friction this phase (fast sequential `input tap`+`input text` calls occasionally dropped/garbled characters or mistargeted a field once the on-screen keyboard shifted the layout, and Android's back button pops Compose Navigation's back stack rather than just dismissing the keyboard when nothing is left to un-focus) — worked around by reading back each field's actual state via `uiautomator dump` after typing it rather than trusting the input call succeeded, and by dismissing the keyboard via the IME's own action key instead of `KEYCODE_BACK`. Noting this here since it's a real gotcha for any future on-device UI automation on this project, not just this phase.
- **`app/google-services.json`** — gitignored rather than committed (a deliberate, disclosed choice: Google's own guidance says it's generally safe to commit since it's a project identifier rather than a secret, but this repo is public and the safer default was chosen). Anyone building this repo fresh needs to place their own copy there first.

## Phase 7 — Profile / account editing ✅ (2026-08-25)

Backend landed same-session ([blood-connect-ju-laravel Phase 27](../Blood_Connect_JU/.claude-progress.md)) — `PATCH /api/v1/profile` (name/email, resets `email_verified_at` when the email actually changes) and `DELETE /api/v1/profile` (password-gated, revokes every token, deletes the user), verified via curl before this phase touched it.

- **`ProfileViewModel`/`ProfileScreen`** — one screen, three cards: **Account** (name/email + "Save account details", "Not yet verified" hint under an unverified email), **Donor profile** (the full flattened onboarding field set — blood group chips, role chips gated by `user.canSelfServiceRole()`, gender chips, DOB, hall/batch/department dropdowns, phone, WhatsApp toggle, availability toggle, last-donation-date — reusing the same update flow Phase 2's onboarding wizard already proved), and **Danger zone** (password-confirm two-step "Delete account" with Cancel/Confirm-delete). - **Two real bugs found and fixed this phase, beyond the backend guard-name bug already caught and fixed before Android work started** (see the Laravel-side Phase 27 entry for `current_password:sanctum`):

## Phase 8 follow-up — stale-on-return screens, and the keyboard covering the field you're typing in ✅ (2026-08-25)

User feedback, three items — the first turned out not to be a bug once traced through the actual compatibility rules; the other two were real and are fixed:

- **"Matching donors shows other blood groups" — investigated, not a bug.** Traced `MatchingDonorsController` → `DonorProfile::scopeMatchingRequest()` → `BloodRequest::DONOR_COMPATIBILITY` end to end and cross-checked it against real ABO/Rh transfusion rules by hand (e.g. an O- request's compatible-donor list is genuinely `['O-']` only — verified directly via `tinker`; an AB+ request's is genuinely all 8 groups, since AB+ is the universal recipient). The list a requester sees is real donor compatibility, not a same-group filter — exact matches are sorted first (`ORDER BY CASE WHEN blood_group = request.blood_group THEN 0 ELSE 1`), so a scan of just the first several rows (which is what surfaced this) looks single-group even though the full list correctly broadens further down. Left as-is rather than restricting to exact-match-only, since that would make the feature medically wrong; flagged back to the user for confirmation this was the actual behavior seen, in case there's a second, different issue not yet reproduced.
- **Real bug: list/detail screens went stale after navigating away and back, without a full app restart.** Root cause: every list-style ViewModel (`RequestsViewModel`, `LeaderboardViewModel`, `DonorDirectoryViewModel`, `ProfileViewModel`, `MyRequestsViewModel`, `DonationHistoryViewModel`) only fetched from `init { refresh() }` — which runs exactly once per ViewModel *instance*, and the instance survives for as long as its NavBackStackEntry stays in the back stack (i.e. the whole time a screen is merely covered by another pushed on top of it, not just while it's freshly created). So creating a request, then navigating back to "My requests" or the feed, showed the pre-creation list until the entry was actually destroyed (leaving the tab entirely, or a cold app restart) — not "some logical issue" in the create flow itself, just a missing refresh trigger on return. Fixed uniformly by adding `LaunchedEffect(Unit) { viewModel.refresh() }` in each of those screens' composables (making `DonorDirectoryViewModel.refresh()` non-private to allow it) — this reruns every time the composable re-enters composition, which Navigation Compose does on every visit to a destination, not just the first. `RequestDetailScreen`/`DonorDetailScreen`/`MatchingDonorsScreen` already did this correctly via `LaunchedEffect(id) { viewModel.load(id) }`, which is why those three were never affected. This is refresh-on-return, not push-driven live sync — a genuinely real-time updating screen (e.g. a response arriving while the detail page is already open, with no navigation in between) would need polling or a websocket, out of scope for what was asked.
- **Real bug: the keyboard covered whatever you were typing, with no way to scroll it into view.** `enableEdgeToEdge()` (added back in Phase 1) turns off the system's own window-resize-on-IME behavior, which is what `android:windowSoftInputMode="adjustResize"` in the manifest used to actually depend on — so every bottom-of-form field (Danger Zone's password, Create Request's contact number, the tail end of Register) sat directly under the keyboard with the screen never resizing around it. Fixed with a single `Modifier.imePadding()` on the root `Scaffold` in `MainActivity` — one fix, applies to every screen, since they all already scroll their content in a `Column.verticalScroll()` and Compose's default focus-brings-into-view behavior does the rest once there's headroom to scroll into.
- Build verified clean. **Live-verified on a real device against production**: confirmed the "Confirm password" field (Register) and "Contact number" field (Create Request) — both previously fully hidden under the keyboard — now sit visibly right above it as soon as they're focused; confirmed the refresh fix specifically by posting a real request, navigating away without restarting the app, and landing back on "My requests" to see it show up immediately (previously required a full app kill to see). Test account and its request cleaned up afterward.

## Full alignment/content audit ✅ (2026-08-31)

A deliberate pass over every screen and shared component in the app — not chasing a specific bug report, just reading every Composable end to end and cross-checking each one live on the physical device — looking specifically for layout/alignment defects the "does it work" testing in earlier phases wouldn't have caught. Found and fixed three real, reproducible classes of bug:

- **Empty-state subtitles not actually centered.** `MyRequestsScreen`, `MatchingDonorsScreen`, `LeaderboardScreen`, `DonationHistoryScreen`, and `NotificationsScreen` all share the same empty-state shape — a `Column(horizontalAlignment = CenterHorizontally)` wrapping a title `Text` and a longer subtitle `Text`. Centering a `Column`'s children only centers each `Text` as a whole block; it says nothing about how a *wrapped* Text's own lines align inside that block, which defaults to start-aligned. Every subtitle here is long enough to wrap to two lines on a phone screen, so despite the "centered" empty state, the second line was always sitting flush-left under the first — no visible symptom for the copy that happens to fit on one line, wrong every time it doesn't. Fixed by adding `textAlign = TextAlign.Center` to every title/subtitle pair in all five screens. Confirmed live: Donation History's empty state (verified by leaving no real donation history) now wraps its two-line subtitle with both lines genuinely centered, not ragged.
- **Two list rows that could collide instead of truncating.** `DonorDetailScreen`'s `DonationHistoryCard` row and `RequestDetailScreen`'s `ResponseRow` both paired a name/title `Text` against a second `Text` (a date, a status label) using a plain `Arrangement.SpaceBetween` Row — no `weight`, `maxLines`, or `overflow` on the first `Text`. `DetailRow` in that same `DonorDetailScreen` file already carries a code comment explaining why this exact shape is wrong ("SpaceBetween only reserves space when there's width left over... lets a long value run into the next field with no gap") and was already fixed there — but the fix was never carried over to the other two call sites in the same file and in `RequestDetailScreen`. A long hospital name or donor name would have run straight into the date/status text with no gap or truncation. Fixed both to match the already-established `weight(1f)` + `maxLines = 1` + `TextOverflow.Ellipsis` pattern `DonorRow`/`RequestCard`/`DonationHistoryScreen`'s own `DonationRow` all already use correctly. Confirmed live against a real response row (a full name plus "Responded" status) — clean gap, no crowding.
- **The Requests tab's "post a request" FAB used Material3's default `primaryContainer`/`onPrimaryContainer` colors** (`FloatingActionButton` doesn't inherit `primary` by default) — which in this theme's color mapping (`Theme.kt`) resolves to `BcAccent`, a pale pink. Every other primary-action surface in the app (the Home dashboard's "Post a blood request" CTA card, every "Save"/"Post"/"Confirm" button) uses the vivid `BcPrimary` red instead, so this one button read as washed-out/disabled-looking next to the rest of the app's own visual language, purely because nothing had ever set its color explicitly. Fixed by passing `containerColor = MaterialTheme.colorScheme.primary` / `contentColor = MaterialTheme.colorScheme.onPrimary` explicitly. Confirmed live: solid red, matching the rest of the app.

No other structural issues found — every other screen (Login, Register, Onboarding, Home, Donor Directory, Donor Detail, Leaderboard's populated state, Profile's full form, Settings, Create Request) was read in full and checked live on-device; padding/weight/alignment usage elsewhere was already consistent, including several places (`DonorRow`, `RequestCard`, `DetailRow`, `AppBottomBar`'s selected-color fix, `ChipColors`' selected-chip-contrast fix) that carry their own prior-bug-fix comments from earlier phases and were confirmed still correct, not just present. Build verified clean (`installDebug`); no unit/instrumented tests exist in this project to run (only the default template's placeholder tests).
